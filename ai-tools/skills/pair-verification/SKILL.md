# Pair verification

Make each verification step reviewable and its conclusion traceable to actual output. Adapt the scenarios to the change; keep the command-and-evidence structure consistent across runs.

## Authorization and interaction

- Default to guidance and commands for the user to run. Read-only inspection is allowed. For initial local bootstrap, the agent prepares the directory and initial files, requests approval as described below, and creates them after approval instead of giving the user setup commands.
- Do not change local or external state without an explicit request for that specific action or a clearly delegated execution scope. “I want to” states a goal; “help me” requests guidance. Invoking this skill does not itself authorize mutations.
- Authorization to edit, run a cluster mutation, stage, commit, push, or publish is separate. Tool permissions do not supply task authorization. Ask briefly when execution intent is ambiguous.
- Within an explicitly delegated scope, continue without repeated confirmation. Pause before an action outside that scope or when an unexpected result invalidates the next step.
- In paired guidance, prepare and show one actionable numbered step at a time. Save every command or command block in a script beside its corresponding output log, with exactly the same basename: `001-baseline.sh` and `001-baseline.log`. Before writing any script file, show its complete proposed contents, exact destination, purpose, expected evidence, and any mutations to the user and wait for explicit confirmation of that script. This includes bootstrap scripts and revisions; do not write an unapproved draft to a temporary script file. Syntax-check an in-memory draft through stdin if useful. After confirmation, save the approved contents, syntax-check the saved script, and always make it executable with `chmod u+x`. The user explicitly authorizes that executable-bit change for verification scripts without separate confirmation. The user runs the script unless execution is separately delegated. Do not source these scripts. Batch independent checks into one step when useful; separately executed blocks or monitors get distinct script/log pairs. If the user requests a complete runbook, provide it without implying it has run.
- Wait for the user to report completion, then read the corresponding log directly from the shared filesystem before choosing dependent steps. Do not routinely ask the user to paste output; collecting evidence for agent inspection is the primary purpose of the logs. If a log is missing, incomplete, or inaccessible, investigate the path and execution status first; request only the missing information when direct access is unavailable.
- Assume the user's working directory is the active pair-verification directory once bootstrap is complete. Give copyable commands relative to it, such as `./003-kas-hold.sh`, and use local filenames for logs and artifacts. Do not repeatedly ask the user to change directories or prefix commands with the repository/run-directory path. At bootstrap, give the one-time `cd` into the created directory; for a new monitor terminal, state that it should open in the same directory. Keep explanation outside command blocks. Use explicit paths only when accessing something outside the run directory or when resolving paths through agent tools. Identify separate terminals for concurrent monitors and explain how to stop them.

## Establish the run

1. Read applicable repository instructions and any relevant existing runbook or verification artifacts. For OpenShift OAuth/OIDC transitions, read [the scenario reference](references/openshift-oidc.md).
2. Establish the target PR/branch SHA, tested image digest when applicable, cluster/context, authentication mode, relevant feature gates, and health baseline. Do not print credentials to establish identity.
3. For repeat verification, recover the previous verified SHA from evidence and history. Handle rebases by comparing actual trees; do not infer the delta solely from current commit dates. Label an uncertain baseline explicitly.
4. Map behavioral changes to scenarios and pass criteria. Distinguish checks already passing for the target SHA from manual checks still needed. Do not expand to unrelated testing automatically.
5. Identify prerequisites, temporary changes, and their restoration steps before the first mutation. Preserve pre-existing settings and overrides. Agree on the scenario scope and whether the user or agent executes changes.
6. Prepare the initial local bootstrap before presenting verification commands. Resolve the exact run-directory path and draft a brief, human-readable `README.md` stating this verification's aim, target revision/PR, scope, and intended success. Draft `run.md` with the known baseline, planned scenarios, authorization scope, and next step. Keep the README to a short paragraph or a few bullets; put detailed progress elsewhere.
7. Request the user's approval to create that exact directory, `README.md`, `run.md`, `000-setup.sh`, and `000-setup.log`. Show the complete `000-setup.sh` contents before requesting confirmation; each later script also requires confirmation of its full contents before writing. Present the path and a concise description of the proposed contents so the approval is concrete. Explain that this skill requires approval for the agent's initial local bootstrap, citing this section when asking. Do not substitute a command block for the user to execute. If the user has already explicitly approved this run's bootstrap and the exact proposed script contents, do not ask for that same approval again; general authorization to prepare verification does not replace confirmation of each new or changed script. After approval, the agent creates the artifacts itself using the command-and-evidence pattern. Authorization to prepare scripts does not authorize executing them, later unrelated file edits, cluster changes, Git operations, or publication. If approval is declined, keep the prepared material in the conversation and wait for the user's direction.

## Present and evaluate each step

Use a stable step number and short purpose. Include:

- **Prerequisites:** only facts needed for the step to be meaningful.
- **Commands and script:** show the full proposed script, including the exact verification commands and self-contained logging wrapper, and obtain confirmation before writing it. Save the confirmed contents in the matching step script and make it executable with `chmod u+x` without a separate approval request. Give the user a short `./001-baseline.sh` invocation from the assumed verification working directory; its shebang selects Bash. Resolve the log from the script's own directory and basename so it works from any working directory and needs no sourced helper or prior exported variable. Explicitly wrap the step in a subshell with a colored `PS4` and local `set -x`, capturing combined stdout/stderr through `tee -a` to its matching log. Use `set +x` outside the wrapper so unrelated commands are not traced. Do not define a persistent wrapper function or enable global tracing. See [the script and logging pattern](references/logging.md). Replace placeholders before execution; do not reuse old cluster addresses, revision numbers, or image digests blindly. Syntax-check Bash scripts with `bash -n` before handing them over; do not execute their verification payload as a validation shortcut.
- **Expected evidence:** concrete observations and pass criteria, including the condition for proceeding. Mark example output as illustrative.
- **Actual result:** read the log directly, check its latest attempt and terminal status, and summarize observed output with relevant timestamps/line references, interpretation, and the next action. Never fill this field from expected output or from the existence of a script. Treat logs without a final status as incomplete until execution or intentional monitor termination is understood.
- **Restoration:** how this step's temporary changes will be restored, if any.

After a failure or unexpected result, inspect it before continuing. Distinguish a failed check from a failed command. Do not treat forbidden access, timeouts, or transport errors as proof that a resource is absent. For absence assertions, establish a successful list or an explicit NotFound response.

For asynchronous transitions, record intermediate states as well as final convergence. Correlate resource and rollout observations with the configurations actually consumed by each running or pending component. A changed source object alone does not prove adoption. Sampled monitor output gives observations within its sampling interval; do not claim exact ordering or uninterrupted availability beyond that evidence.

## Evidence and continuation

Use a run directory named exactly `pair-verification-{short-sha}-{yyyymmdd}`, under the working directory at bootstrap unless the user chooses another parent. After bootstrap, assume the user works inside the created run directory. On resumption, reuse the active directory rather than creating a nested run directory. Resolve `short-sha` with `git rev-parse --short <target-revision>` for the revision being verified; record the full target SHA in `run.md`, and use the run's start date in the user's timezone. Do not change the name at midnight. Store all relevant run files there: concise `README.md`, progress record, matching numbered scripts and logs, manifests, patches, snapshots, and monitor output. Avoid temporary evidence files elsewhere; keep credentials out of the evidence directory.

Keep existing evidence intact. If the directory already exists, inspect its progress record and establish whether this is a continuation before appending; never silently overwrite it. Use [the run template](assets/run-template.md) for `run.md` and stable script/log pairs such as `003-kas-hold.sh` and `003-kas-hold.log`. Retries of an unchanged script append to its log with fresh command headers and timestamps. If commands change after execution, preserve the executed script and log and issue a new numbered pair, so saved instructions still describe the recorded evidence. Distinct scenarios or concurrent monitors use their own pairs. Resolve an absolute `PV_RUN_DIR` from the script location so changing directories or opening another terminal does not redirect evidence accidentally.

Record the command, working directory/context, timestamp, exit code when captured, relevant stdout/stderr, and interpretation. Use an explicit Bash session for the documented `PS4` and `PIPESTATUS` syntax. Set `pipefail` and `errexit` inside the step subshell; capture `PIPESTATUS` immediately after the outer `tee` pipeline so a successful logger cannot hide a failed step. Keep tracing, shell-option changes, and temporary command variables inside the subshell where possible. Record long-lived monitors' termination separately from check failures.

Never log passwords, bearer tokens, private keys, complete credential-bearing kubeconfigs, or shell tracing of credential commands. Extract only the evidence fields needed, such as webhook server and TLS identity. Historical logs may contain secrets: inspect narrowly and redact before quoting or sharing. Do not silently discard relevant failures while trimming output.

For initial bootstrap, follow the approval-and-agent-execution workflow above. Preparing step scripts and reading their logs are distinct from running the verification commands. Confirmation to write a specific script and permission to make it executable are separate from execution authorization. Do not ask again for the same confirmed script contents or for the executable-bit change; obtain confirmation before writing any new or changed script. For other evidence writes outside an authorized scope, maintain progress in the conversation and provide commands/content for the user to save. On resumption, read the progress record and actual logs directly, identify the exact next step, and recheck live assumptions that may have changed. Do not rerun mutations merely because context was lost.

## Finish

Report the exact revision/image verified, scenarios passed/failed/not run, material evidence limits, and restoration status. Restore temporary state only within authorization; otherwise provide the remaining commands and mark restoration pending. Confirm restoration by read-only checks rather than inferring it from a successful patch.

Separate newly verified behavior from previous verification carried forward by inspection. Draft a PR verification comment if requested; publishing it requires explicit authorization. Link relevant evidence without embedding credentials or asserting checks that were not performed.
